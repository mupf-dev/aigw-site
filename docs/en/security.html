Guardrails & security

How ai-gw inspects prompts and responses – PII, prompt injection, system-prompt leaks, data exfiltration via links, languages, external content safety – and which protections apply inside the gateway itself.

An AI gateway sees every request and every response. That makes it the right place for protective rules – and obliges it to handle data, keys and outbound connections carefully itself. This page covers both.

Guardrails as plugins#

Guardrails are ordinary plugins in the chain. They are bound globally or per organization, team, key or model group, inherit inwards, can be locked against overrides and have a defined failure behavior (failMode: closed rejects, open lets through). A typical order: cheap checks that reject early first, then masking, then external services on the already masked text.

PluginPhasePurpose
prompt-filterrequest, optionally response and streamword and phrase lists, regex rules, prompt-injection heuristics, length and count limits, invisible Unicode characters
piirequest, response, streamdetect personal data and secrets; mask, remove, reject, pseudonymize (with re-identification) or count
prompt-leakrequest, response, streamsystem-prompt leaks via a canary token, optionally verbatim excerpts
link-guardresponse, streamprevent exfiltration via links and images to foreign domains
languagerequest, optionally responseallowed or blocked languages
content-safetyrequest, response, streamexternal checks via Azure AI Content Safety, OpenAI Moderation or a custom guard model

Rejected responses come back in the client's format (e.g. finish_reason: content_filter or a refusal in Anthropic format) and carry the x-aigw-guardrail header naming the triggering plugin.

PII and secrets#

PII detection is a dedicated rule-based engine without an external model. It detects e-mail addresses, phone numbers (international and German), IBANs (with checksum for 75 countries), credit cards (BIN ranges and Luhn), German tax IDs, social security, ID card and passport numbers (each with check digit), IP addresses, credentials in URLs and API keys and tokens of common services – plus an entropy heuristic for unknown secrets.

  • Actions per category: mask ([EMAIL_1]), remove, reject, pseudonymize with re-identification in the response, or only count.
  • Allowlist for known, harmless values (such as your own support address).
  • Fast: a 4 KB prompt with findings is checked in about 23 µs (median, one core).
  • On request the same engine masks content in the request log.

The engine deliberately does not detect names and postal addresses – without a language model they would be too error-prone. An external service or guard model can be plugged in via content-safety or a webhook instead.

Prompt injection and invisible characters#

prompt-filter weighs known injection signals (“ignore all previous instructions”, role switches, chat-template tokens …) and rejects above a threshold or only flags. It also detects invisible Unicode characters – tag characters (“ASCII smuggling”), zero-width, bidi and format characters – and strips them or rejects; legitimate cases such as emoji sequences or joiners in Persian and Indic scripts are preserved. Word and regex rules can also check the output, in streams across chunk boundaries.

System-prompt leaks#

prompt-leak inserts a random canary token into the system prompt – new per request or stable, so that providers' prompt caching keeps working. If the token appears in the response, stream, tool arguments or reasoning, the output is blocked or the token removed; it never reaches the client or the log. Optionally the plugin detects verbatim excerpts of the system prompt via word n-grams.

Exfiltration via links#

An injected instruction – for example in a tool result or a document – can make a model write confidential data into an image URL. The chat client loads the image when rendering, without a click, and the data ends up with the attacker. link-guard removes images pointing to foreign domains and can defuse links, query parameters or long paths; allowed domains are configured explicitly.

External content safety#

content-safety queries Azure AI Content Safety (via API key or Microsoft Entra ID), OpenAI Moderation or a custom guard model (e.g. Llama Guard) through a model group of the gateway. Thresholds per category, checks on input, output or both, output buffered or sentence by sentence in streams; tool-call arguments are checked too. The guard model's costs are recorded and can be capped.

Default profiles#

ProfileContents

Opengenerous size limits only; payload logging metadata only

Profiles are applied to a level via UI or admin API – with diff and dry run.

Tools and MCP#

Applications send the tools a model may call with every request. ai-gw inventories them, detects descriptions changed after the fact (“rug pull”), checks descriptions for injection signals and enforces tool policies: allow, strip, reject, observe or approval required – including tool calls in the response. MCP servers behind the gateway are invisible to everyone by default; grants apply per team and key down to individual tools. More: Tool policies, MCP gateway.

Security of the gateway#

  • Secrets: credentials encrypted (AES-256-GCM), master key never in the database, rotation via aigw config rekey. API keys only as hashes; logs never contain Authorization or key headers, and incoming tokens are never forwarded to providers.
  • Outbound connections: a shared component with SSRF protection – the URL is checked on save and the target address on every connection after name resolution (against DNS rebinding), no redirects, size and time limits. Private targets only after an explicit, narrowly scoped approval by global admins.
  • Listeners: maximum concurrent connections, read timeouts against Slowloris, HTTP/2 limits, body limits; running streams are unaffected.
  • Admin access: OIDC with PKCE, session cookies with the __Host- prefix, SameSite=Strict and CSRF tokens, a role model with team boundaries, a one-time bootstrap token valid only until the first admin.
  • Sandboxed plugins: WASM modules without file system, network or environment, with limits on CPU, time and memory and optional Ed25519 signature enforcement – see WASM plugins.
  • Traceability: audit log with hash chain, verifiable via API, UI and aigw audit verify.
  • Supply chain: cargo deny with license and advisory checks, pinned UI dependencies with a minimum age for new packages, a license overview of all dependencies.

The project has gone through an internal security review; the resulting operational recommendations are under Operations and hardening. Please report vulnerabilities confidentially: Report a vulnerability.
